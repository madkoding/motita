Why you can trust “done”

The model proposes. Your code disposes.

Other agents grade their own homework, and a language model will always produce a sentence that sounds like success. motita splits every task in three, and the model only ever gets to propose. A real check — your tests, your linter, your build — is the only thing that can declare a task done. If it fails, the agent gets the real error and tries again. If it can't pass, it says so and stops.

You don't have to configure the check: the wizard's default, anchor.kind: auto, finds the one your project already has.

Layer A · the anchor

Deterministic code, not AI

By default it runs the gate the project declares: .motita/anchor, a Makefile's check/test, go test, a package.json's lint/typecheck/test, cargo test, pytest. Or your own command, exit code and output pattern. When the gate was already red before the task, only a new failure blocks it. It cannot be talked into a different answer.

Layer B · reasoning

Any provider, one client

One hand-written client for every provider. Replies are held to a schema where the provider can enforce one, and every token is counted per agent.

Layer C · the sandbox

Honest about its limits

Runs the action under real limits — and tells you what it could not apply, instead of pretending the isolation is stronger than it is. A toolchain the agent installs once stays on its PATH for every session after.

Your repository stays yours

Every conversation on its own branch.

Point motita at a repository and each session works in a git worktree of its own, on branch motita/<session>. Your checkout is never the one being edited, and two sessions never step on each other.

Checkpoints

Go back a turn

Every turn is a checkpoint. Going back rewinds the conversation, and the files too when you ask — after the current state is saved, so going back is itself reversible.

Integrate

It merges its own work

It commits the session's work and merges it into the project's branch. The session then becomes read-only, and continue opens a fresh one from the updated base.

Background agents

Hand off a piece

Each helper works in its own worktree from a snapshot of the tree — uncommitted work included — and reports back with the one command that brings its branch in.

Delete

Asked first, with the list

Deleting a session or a project names the files that would be lost before anything goes, and gives the worktrees back.

Safety

Fast where it's safe. Asks where it isn't.

A guardrail that interrupts you for make gets switched off within a week. So motita runs the everyday work silently, stops for anything that reaches past your project, and has a floor of commands it refuses no matter what — with no flag, key or variable that relaxes it.

ALLOW It changes nothing, or only the workspace you pointed it at. make, go build, npm test and your own ./scripts/* run silently.
ASK It reaches the network or the system, writes outside the workspace, or can't be classified. You are asked before anything runs — once, or for the whole session.
DENY The floor, always: mkfs, partition editors, dd with an output, the power verbs, and rm/mv/cp/ln aimed at /, ~, a system path, or the tree that contains your workspace.
an ASK, live

Plan mode is structurally read-only. It calls tools through a path that never invokes a shell, so pipes, redirections and metacharacters aren't blocked — they're syntactically unreachable. And the browser link carries its token in the URL fragment, traded once for a cookie holding an HMAC of it.

It gets better with you

It learns from you, not from a retraining pipeline.

A library of procedures: how a kind of work is done, the commands that work, the pitfalls someone already paid for. Eight ship inside the binary, the agent writes new ones when it learns something, and a project can keep its own. They are files — read them, fix them, version them.

  • /good and /bad land on the procedures a turn actually used, and the library is searched by what has worked before. No fine-tuning, no extra bill.
  • A curator keeps the shelf tidy without a model: unused procedures are marked stale, then archived — never deleted — and a pinned one is never touched.
  • Retries that learn something: a failed check sends back the command, its real output and a structured verdict, so the next attempt fixes the actual problem instead of re-rolling the dice.

Running it

One binary: configure it, run it, serve it, script it.

After the installer, the binary is the whole program: the terminal interface, the gateway and the browser page are the same file. With no configuration on the machine, the first run launches the wizard — and the step no other agent makes you answer is the anchor: the command that proves a task is really done.

First run · configure

# the wizard: provider → connect → model → check → review
motita config

# or just start it — with no config found, the wizard runs itself
motita

It saves ~/.motita/motita.yaml; /config runs it again from inside the interface and keeps what you already have.

The terminal interface

# no arguments: a gateway is started for this interface, in-process
motita

# one-shot, scriptable: exit 0 when the check passed, 1 when not
motita -task "fix the failing test in internal/policy"
motita -p "how many files are there?"

/task and /plan, /models, /goal, /agents (or Ctrl+G), /git, /update — ? lists every command and key.

The gateway, every setting and the exit codes are in the reference.
