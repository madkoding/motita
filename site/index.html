Motita

Every other agent asks you to trust it. motita runs a real check, and only the check can declare the task done. If it fails, the agent gets the real error back and tries again. If it can't pass, it says so and stops.

$ curl -fsSL https://madkoding.github.io/motita/install.sh | sh
> irm https://madkoding.github.io/motita/install.ps1 | iex

One static binary. No Docker, no runtime, no dependency tree. It runs on a 2008 netbook with 484 MB of RAM.

Running it

One binary: configure it, run it, serve it, script it.

After the installer, the binary is the whole program: the terminal interface, the gateway and the browser page are the same file. With no configuration on the machine, the first run launches the wizard — and the step no other agent makes you answer is the anchor: the command that proves a task is really done.

First run · configure

# the wizard: provider → connect → model → check → review
motita -init

# or just start it — with no config found, the wizard runs itself
motita

Five steps, ↑ ↓ through every list: the provider, how to connect (sign in with your account, or paste a key), the model, the check — detected from the project by default — and a review where nothing has been written yet. It saves ~/.motita/motita.yaml (-init -config path puts it elsewhere); /config runs it again from inside the interface and keeps what you already have.

The terminal interface

# no arguments: a gateway is started for this interface, in-process
motita

# a gateway someone else runs — this process runs no commands
motita -connect 127.0.0.1:7477 -tui

# one-shot, scriptable: exit 0 when the check passed, 1 when not
motita -task "fix the failing test in internal/policy"
motita -p "how many files are there?"

Inside the interface: /task and /plan switch between doing work and read-only exploration; /models, /reasoning, /config; /sessions and /attach move between conversations; /agents (or Ctrl+G) shows the background agents; /good /bad /value; /update installs the newest release after checking it against its SHA256SUMS; /help for the rest.

The gateway

# in the background, outliving the shell that started it
motita gateway start
motita gateway status
motita gateway stop

# foreground, gateway only: no interface, for remote clients
motita -serve -gateway 127.0.0.1:7477

gateway start prints the interface link — http://127.0.0.1:7477/#t=<token> — which a browser opens once to trade the fragment for a cookie. The same port serves the page and its /v1/... API, so there is no CORS and no second server. gateway.allow in the YAML says who may reach it. An update applied to a -serve gateway restarts it on the new binary, with the same flags.

Configuration

# -config names a file; without it: ~/.motita/motita.yaml,
# then ./motita.yaml, then the built-in defaults
motita -config configs/agent.yaml.example

# check a file without running anything (no model call, writes nothing)
motita -validate-config

# the sandbox limits this machine can apply — and what it cannot
motita -isolation

Every setting also takes a MOTITA_* environment override, for containers and secrets. A pasted key goes to ~/.motita/motita.env and a login to ~/.motita/auth/<provider>.json, both 0600, never into the config — so the config can be committed and shared.

The architecture

The model proposes. Your code disposes.

motita splits every task in three, and the model only ever gets to propose. The one rule that makes it work: the model can propose a PASS, but only layer A can declare one. Without a real check, nothing is ever declared done — there is no "trust me" mode. The wizard's default, anchor.kind: auto, finds the check the project already has.

Layer A · the anchor

Deterministic code, not AI

By default it runs the gate the project declares: .motita/anchor, a Makefile's check/test, go test, a package.json's lint/typecheck/test, cargo test, pytest. Or your own command, exit code and output pattern. When the project's gate was already red before the task, only a failure that is new blocks it — and the verdict names the checks that were red. It cannot be talked into a different answer.

Layer B · reasoning

Any provider, one client

A hand-written client for OpenAI (chat and Responses), Anthropic, Gemini, Copilot, Qwen and Ollama — and your Claude subscription through the official Claude Code CLI. Replies are held to a schema where the provider can enforce one, and the tokens every call reports are counted per agent.

Layer C · the sandbox

Honest about its limits

Runs the action under real limits — and tells you what it could not apply, instead of pretending the isolation is stronger than it is. HOME and temporary files live outside your repository, and a toolchain the agent installs once stays on its PATH for every session after.

Providers

Your subscription, or any API.

Sign in with the account you already pay for, or paste a key. Logins are renewed before they expire, and an API key always wins over a stored login. Nothing else in the agent knows which provider is behind it.

claude-code

Your Claude Pro or Max plan, through Anthropic's own claude CLI after claude auth login. motita never reads those credentials.

codex

Sign in with ChatGPT (Plus, Pro, Business) or an OpenAI key, over the Responses API.

copilot

A GitHub device-code login with an active Copilot subscription; the session token is renewed on its own.

openai

An API key, against OpenAI or any OpenAI-compatible host: Groq, OpenRouter, DeepSeek, your own box.

ollama

A local server needs nothing at all; Ollama Cloud takes a key. The wizard lists the models your server really has.

anthropic

An Anthropic API key, over the Messages API.

gemini

A key, a Google login with your own OAuth client, or gcloud's application-default credentials.

qwen

A qwen.ai device-code login, or a DashScope key.

Why it holds up

Retries that learn something.

When a check fails, the agent gets the failing command, its real output and the structured verdict back. It fixes the actual problem instead of re-rolling the dice. 

# The end-to-end test asserts the result on the FILESYSTEM, not in what the agent says.
# Its simulated model gets it wrong on purpose, then corrects itself — every commit.
attempt 1  FAIL  anchor: exit 1 — "expected output.txt to exist"
           the real error goes back to the model
attempt 2  PASS  anchor: exit 0 — output.txt present and matching

# Your exit code means something:
0  every task passed its check
1  a task failed — with the reason in the message itself
2  bad configuration

Long tasks

Rounds spent on the work, not on the plumbing.

A real task takes dozens of rounds. Every one the agent spends fighting its own tools is one it does not spend on yours, so the loop is built to waste none.

  • Replies that cannot come back in the wrong shape. The next action is a JSON object held to a schema where the provider enforces one; elsewhere, a reply in another shape is read rather than thrown away.
  • Files written as they are. write_file and edit_file put content on disk exactly — tabs and quotes included — with no heredoc or script to escape it, and an edit that does not match says so.
  • A check it ran itself and saw fail is not walked away from: a claim of done over it is sent back, even when | tail hid the exit status.
  • Toolchains installed once. Go, Node or make unpacked into the tools directory are on PATH in every later round and every later session — and the check sees them too. Long gates get sandbox.check_timeout, 15 minutes by default.

Projects & sessions

Every conversation on its own branch.

Point motita at a repository and each session works in a git worktree of its own, on branch motita/<session>. Your checkout is never the one being edited, and two sessions never step on each other.

Checkpoints

Go back a turn

Every turn is a checkpoint. Going back rewinds the conversation, and the files too when you ask — after the current state is saved, so going back is itself reversible.

Integrate

The agent merges its own work

It commits the session's work and merges it into the project's branch. The session then becomes read-only, and continue opens a fresh one from the updated base.

A report you can check

Evidence, not adjectives

A finished task answers with what changed, how it was verified and with what result, the risks and the next steps — the changed files listed, and screenshots first when the change is something you can see.

Delete

Asked first, with the list

Deleting a session or a project names the files that would be lost before anything goes, and gives the worktrees back.

Background agents

Hand off a piece. Keep working.

The agent can start agents of its own for independent pieces of a task — a test suite, the docs, an investigation — and keep going while they run. Each one works in its own worktree, on its own branch, from a snapshot of the tree as it was, uncommitted work included. 

# Ctrl+G or /agents in the terminal; the AGENTS drawer in the browser
Agents  1 running · 48.2k tok
 /  main · fix the session export     2m14s   31.0k tok  r12
 /  write the export tests             1m02s   11.9k tok  r6   running: go test ./internal/export
 √  update the reference               0m48s    5.3k tok  r4   motita/sub/…-a2 · 1 file changed
  • spawn_agent and wait_agents. A finished agent reports on its own: what it did, the files it changed, and the one command that brings its branch in.
  • Held to the project's own gate, not to a check that states the whole task — the main agent's check judges the merged result.
  • Bounded by agent.max_parallel, 3 by default. A claim of done with agents still running is sent back once; insisting cancels them.
  • Nobody is interrupted by a background agent: "allow all commands for this session" covers it, and anything else is refused instead of asked.
  • Real tokens, as each provider reports them — input, output and cache — per agent and in total.

The browser interface

Same port, same conversation, any screen.

The gateway serves a web interface from its own port — no second server, no CORS. The token rides in the URL fragment, which a browser never sends, and is traded for a cookie holding an HMAC of it, so a lifted cookie is not a reusable credential. On a phone it installs as an app.

The conversation

Answers rendered as Markdown, streamed live and resumed after a dropped connection. The commands of a turn collapse into a counter you open when you want them.

Drawers

The model's reasoning as it writes it, a terminal with every command and its output, and the agents with their purpose, time and tokens.

Projects

Sessions grouped by project in the sidebar, checkpoints to go back, the report with its screenshots, and an approval shown with the command whole.

Windows

The skill library, the tasks that fire on their own, and failures reported where you will see them.

It learns

From you, not from a retraining pipeline.

A library of procedures: how a kind of work is done, the commands that work, the pitfalls someone already paid for. Eight ship inside the binary, the agent writes new ones when it learns something, and a project can keep its own. They are files — read them, fix them, version them.

  • /good and /bad land on the procedures a turn actually used, and the library is searched by what has worked before. No fine-tuning, no extra bill.
  • A curator keeps the shelf tidy without a model: unused procedures are marked stale, then archived — never deleted — and a pinned one is never touched.
  • You can see the shelf — every document, how often it was used, a switch to turn one off — in the browser, or through /v1/skills.

The guardrails

Two layers, and only one of them is yours.

The floor is a small, deliberately un-configurable set of commands that are refused no matter what. The confirmation layer is where you decide what interrupts you — and the subtle middle row below is the whole design.

ALLOW It changes nothing, or it changes the workspace you pointed the agent at. make, go build, npm test, python3 build.py and your own ./scripts/* run silently.
ASK It reaches the network or the system, writes outside the workspace, or is something nobody can classify. You are asked before anything runs.
DENY Strict mode: what cannot be classified is refused instead of asked about. And the floor, always — mkfs, the partition editors, dd with an output, the power verbs, and rm/mv/cp/ln aimed at /, ~, a system path, or the tree that contains your workspace.

Rule 2 is the one that keeps the layer alive: a policy that asked about make would be switched off within a week, and then it would protect nothing. There is no YAML key, no environment variable and no flag that relaxes the floor — that's the point. A guardrail an operator can switch off is a guardrail that will be switched off, during the incident it was meant for. What you can say is "allow all commands for this session": one answer for the rest of that conversation, remembered across a restart, and announced every time it is used.

The numbers

Tested the way you'd test something you were about to bet on.

These are measured, not asserted — and the documentation's claims are anchored to the code by tests, so the page cannot drift away from the behaviour.

100%statement coverage in every package that ships — 30 of 31 (./internal/... ./cmd/...), checked one by one so a gap can't hide behind an average; internal/review is the one exception and the CI harnesses in tools/ are counted separately
0external dependencies — go.mod has no require line, and there is no go.sum
9platforms CI builds, with 386 as a first-class target — each one runs its container on Linux, and gets a header and size check on Windows and macOS
18.2–19.2 MiBper static binary, measured across all 9 targets — copy it over scp and walk away

That coverage number isn't a badge. It's the mechanism that found the bugs now documented in the reference: the RLIMIT_CPU that never fired, the process group that kept a 1-second deadline waiting for five, the sandbox directory that got deleted before the validator could look inside it. Every one of them is a test now.

CI reads the ELF header to prove the i386 binary really is 32-bit, and runs the end-to-end tests inside a real 32-bit container before publishing anything. It also runs staticcheck and govulncheck — the standard library ships inside the binary, so a toolchain that has aged out of support hands its known vulnerabilities to whoever downloads it.

That is not left to discipline. The build fails the day go.mod's Go version is no longer one the Go project still patches — asked directly of go.dev/dl?mode=json rather than kept as a note with a date somebody has to remember. Every claim on this page is checked the same way: the "no dependencies" line, and these documents matching their sources.

The interface

A terminal interface you'll actually want to use.

Run it with no arguments and you get a full TUI — written against the standard library alone, so it's the same binary, not a wrapper around something else.

/task   /plan

Switch between doing work and read-only exploration.

/models

Your provider, your key status, and the models it really publishes.

/good   /bad

Tell the agent how a turn went. It lands on the procedures that turn used.

/value

See what it has learned from those verdicts — no fine-tuning, no extra bill.

/sessions   /attach

The conversations the gateway holds, which one has a run in flight, and a move to another.

/agents   Ctrl+G

The background agents: purpose, elapsed time, tokens, what each is doing. The footer keeps the count and the total.

/config   /update

The setup again, applied at once; the newest release, verified before it is installed.

Quiet by default

The commands a turn runs are a counter, not a wall of lines; gateway.show_actions: true lists every one.

Plan mode is structurally read-only. It calls tools through a path that never invokes a shell, so pipes, redirections and metacharacters aren't blocked — they're syntactically unreachable.
